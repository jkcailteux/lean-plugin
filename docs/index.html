What's inside

Four things that earned their place.

No per-tool-call hooks, no dependencies, no background daemon. Hooks run once per session and once per prompt, and the tools are a single zero-dependency Node file.

Repo map

About 1.3k tokens at session start: every tracked file and its top-level symbols as name:line. Claude goes straight to the right file and line range instead of exploring. Cached per git HEAD, never re-injected on resume.

explore −50% turns · symbol lookups −47% to −60% cost

BatchEdit

Many search-and-replace edits across many files in one call, all-or-nothing per file, with a one-line reply. No prior read needed. Every saved round trip also skips a full re-read of the conversation.

edits −80% turns · −50% wall time · 0 failed calls

Context guard

Come back to a 300k-token session after the prompt cache expired and your next message silently re-writes all of it at the cache-write price. lean stops that one prompt and suggests /compact. Send again and it goes through.

−38% to −45% simulated, when you compact on the prompt

MultiRead + RunCompact

Read several files or line ranges in one call; run tests and builds and get back only the failures and the tail. A 320-test run shrinks from ~4,000 tokens to ~300.

removing them cost +10% and 4× the exploring turns

The bigger lever

The real leak isn't tool output.
It's context.

Every turn re-reads the entire conversation. In short benchmark tasks that's cheap. In real, long-running sessions, the turns carrying 120k+ tokens of context are where the money goes, and a session resumed after the one-hour cache expires pays to write all of it again.

So lean pairs its tools with a context policy: compact sooner, and never resume a huge stale session by accident.

The simulation re-prices each recorded turn and charges every compaction a full uncached read, its summary and 30–60k tokens of re-reads afterwards. It can't price detail lost to compaction, which is the trade-off you accept.

What we cut

Most good ideas didn't survive the benchmark.

Each candidate got mechanism tests that prove it works, then a benchmark and a replay of real usage to prove it matters. These all worked as designed. They just didn't pay.

16ideas tested
12cut
4shipped

Read cache

0 identical re-reads in 615 real reads. Claude Code already doesn't re-read.

Outline tool

Never called in 9 sessions. Tools Claude has to choose go unused.

Big-file outline + ReadSymbol

Never fired. The repo map's line numbers already make Claude read ranges.

Data-file summaries

Claude queries big JSON and logs with jq and grep. Nothing to summarize.

Grep junk filter

−43% grep output on a polluted repo, but 0.04% of real usage, and it could hide code in build/.

Bash output compaction hook

0% change. RunCompact already covers it.

Slim mode (no core tools)

+10% cost and 4× the exploring turns. The core tools stay.

Cache-stable session prefix

No measurable effect on prompt caching.

Faster search index

Tools are 0.4% of wall time. The model is the bottleneck.

Write → Edit guard

Full-file rewrites are rare. Under 1% of output.

Dedupe repeat calls

816 repeats added up to ~665 tokens. Not worth a hook.

Parallelize single reads

8 occurrences in all of history.

Version one also ran two hooks on every tool call, about 55 ms each. They're gone: the shipping build adds no per-call latency.

How we measured

A clean fight against vanilla.

Isolated

Every session ran with user plugins, hooks and connectors switched off, so lean faced plain Claude Code and nothing else.

Real and synthetic tasks

3 tasks on a real Next.js app pinned to one commit, 5 on a generated repo built to trigger each feature. Every answer and edit checked automatically.

Reproducible

Throwaway git clone per arm, reset after every run, arms in parallel. The harness, tasks, fixture and raw results are all in the repo.

Claude Opus 5.5 on Claude Code 2.1.301. 80 benchmark sessions in the two composite runs, plus feature rounds; about $45 of API time in total.
